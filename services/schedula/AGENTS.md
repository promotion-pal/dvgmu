# Работа над Schedula

- Перед началом задачи открой [оглавление документации Schedula](README.md) и прочитай разделы по задаче. Если задача касается календаря или редактора портала, сверься с [картой экранов](FRONTEND.md).
- Для первой версии начни с [границ MVP и матрицы ролей](MVP.md). Реализуй путь отдела от нагрузки до публикации и личное чтение. При изменении доступа проверь прямой RPC, URL и публичные каналы с обычными учётными записями. [Полная матрица](ACCEPTANCE.md) относится к расширенному объёму, [справочник API](API.md) описывает сегодняшний код. Условия вывода прежнего расписания приведены в [README](README.md#зачем-пока-нужен-старый-scheduleservice).
- Владелец датированного события — Schedula. Код `apps/fesmu/api/internal/modules/schedula` проверяет сессию и пересылает запрос. Код прежних `ScheduleService` и `ScheduleCollectService` меняй при работе с их данными, входящими или совместимостью ссылок.
- Размещай правила времени, назначения и размещения в `api/internal/service`. Проверку, подбор, публикацию и изменение сверяй на одних примерах. При изменении записи сохраняй транзакционную границу `Storage.Write`, проверку статуса и ревизии. При добавлении внешнего источника сначала изучи контракт владельца.
- Проверяй допуск к RPC в `internal/grpc`, доступ к объекту при его чтении или изменении. При расширении закрытой выдачи отдельно проверь публичную проекцию и метаданные фильтров. Интерфейс получает возможности из `ScheduleFetch`.
- Для изменения API редактируй исходные proto у владельца и из корня запускай `make proto`. Проверь Go- и TS-клиенты, номера полей и совместимость старого вызова. `make proto-check` сравнивает регенерацию с индексом. Изменение БД оформляй следующей миграцией в `api/migrations`.
- На фронтенде используй общий транспорт, фильтры и URL-состояние портала. Изменение периода, публикация или возврат из карточки должны обновлять тот же календарь в исходном контексте. Тестируй нужный сценарий на широком и узком экране без записи экрана.

## Проверки по области изменения

Команды в таблице запускаются из указанного каталога. Для проверок, требующих зависимости, используй окружение проекта.

| Что изменилось | Каталог | Команда |
| --- | --- | --- |
| Расчёт интервалов, периодов, переходов или слотов | `services/schedula/api` | `go test ./internal/service` |
| Состояние, права, миграции или Connect API | `services/schedula/api` | С заданным `SCHEDULA_TEST_DSN` запустить `go test -count=1 -v ./...`. Для `TestScheduleLifecycle` и `TestPersistedCalendarChecksAndCompleteness` нужна отдельная тестовая PostgreSQL с правом создания схем. Без DSN эти проверки пропускаются. |
| Передача личности в шлюзе | `apps/fesmu/api` | `go test ./internal/modules/schedula` |
| URL календаря или групповая подписка | `apps/fesmu/web` | `node --test tests/schedula-calendar.test.ts tests/calendar-feed.test.ts` |
| Портальные виджеты и страницы | Корень | `pnpm --dir apps/fesmu/web build` и ESLint изменённых файлов |
| Структура, размещение контрактов или сборка | Корень | `.claude/skills/fesmu-architecture/scripts/check.sh` |

Для сквозной проверки запусти [локальный стек](README.md) и пройди выбранный критерий с его ролями, экземплярами и ожидаемым результатом. Обнови локальный `schedule-work.md` согласно правилам рабочей копии. При изменении действующего контракта, маршрута или поведения обнови соответствующий раздел документации сервиса.
