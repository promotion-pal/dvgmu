# План реализации сервиса заявок

Развиваем существующий `services/tickets`. Используем Go, ConnectRPC, GORM и PostgreSQL. Сохраняем цепочку `internal/grpc → internal/service → internal/storage`, а API описываем в `contract/tickets`. Команда `make proto` обновляет Go- и TypeScript-контракты, которыми уже пользуется кабинет.

## Что меняет текущий репозиторий

- У старой таблицы `tasks` только ID, заголовок и дата создания. У записей нет автора, услуги и маршрута. Предлагаю завести отдельную таблицу `requests` в базе tickets и сохранить старые строки до согласования переноса. Для нового API использовать отдельный `RequestService`. Старые `CreateTask` и `ListTasks` должны быть закрыты или выведены из эксплуатации при переключении кабинета, чтобы публичный общий список и свободное создание задач не остались параллельным путём.
- MDM умеет читать профиль по ID, но это ещё не серверная аутентификация и не источник полномочий для заявок. Фронтовый `DEFAULT_USER_ID = 1n` и заглушка `login` для авторизации непригодны. В репозитории есть отдельные protobuf-определения для оргданных, но в используемом API MDM нет подтверждённого контракта на рабочие области, подразделения и право исполнителя работать с конкретной услугой.
- Во фронте есть поле загрузки файла. Серверного контракта хранения, подтверждения принадлежности временных файлов и скачивания по правам в репозитории не найдено. Аналогично не найден административный API платформы, в который можно встроить настройки заявок.
- `db/migrations/loader.go` отдаёт Atlas схему GORM, а Goose применяет встроенный SQL при старте. Добавлять версионные миграции в `db/migrations/task/`. Проверить, что Atlas видит новые модели и не предлагает удалять ограничения и индексы, описанные вручную в SQL. Старую миграцию оставить для воспроизводимости установки.
- Контроллер уже использует ошибки Connect. Для нового API закрепить `InvalidArgument` для ошибок полей, `Unauthenticated` для отсутствующей сессии, `PermissionDenied` для запрета операции, `NotFound` для недоступной по UUID карточки, `FailedPrecondition` для запрещённого перехода и `Aborted` для устаревшей версии. Добавить типизированные детали валидации и не возвращать клиенту ошибки SQL.

## Интеграции и решения владельца процесса

| Что подключаем | Ожидаемый контракт | Что можно делать до подключения |
| --- | --- | --- |
| Авторизация | Проверенные сервером учётные данные → ID пользователя в контексте RPC | Интерцептор и тестовые профили только для тестов и локального запуска. В production доступ по умолчанию закрыт |
| Оргструктура и полномочия | ID пользователя → актуальное подразделение, роли и рабочие области. Услуга и подразделение → допустимые исполнители и согласующие | Проверки действий и видимости на локальном наборе ролей. Хранить внешние ID без межбазовых FK |
| Файлы | ID временного файла → владелец, ключ, имя, тип, размер, срок хранения и состояние привязки. Авторизованное скачивание → поток или временная ссылка | Метаданные, проверки доступа и тесты на локальном адаптере |
| Администрирование | Подтверждённые полномочия → управление каталогом и маршрутами в своей области | Локальные данные для тестов и прикладные операции управления |

В приложенном ТЗ есть примеры уборки, ремонта и Wi-Fi, полный стартовый каталог вынесен в основное ТЗ. До релиза получить каталог и схемы полей, реальные ID подразделений, маршруты, полномочия очереди разбора, согласующих и подтверждающих, лимиты файлов и настройки SLA. Отдельно согласовать судьбу старых задач, часовой пояс смены года для номера и правила повторного открытия. Пока действуют рабочая матрица ТЗ, приоритет точного маршрута, отдельный годовой счётчик и очередь разбора при отсутствии однозначного маршрута.

## Последовательность реализации

1. **Контракты и схема.** Добавить направления, услуги с версиями схем, правила маршрутизации, заявки, счётчики номеров, события и вложения. В заявке хранить внутренний ID, публичные UUID и номер, ссылку на версию схемы услуги, название и описание, статус и приоритет, автора, его подразделение при создании, ответственное подразделение, исполнителя, специфические поля, результат, состояние ожидания и даты из ТЗ. Под очередь разбора выделить явное состояние маршрутизации. Даты хранить как `timestamptz`, отдавать через protobuf Timestamp. Добавить уникальность UUID и номера, ограничения справочников и индексы для списков по автору, очередям, исполнителю и истории.
2. **Каталог, регистрация и маршрутизация.** Выдавать доступные активные услуги со схемами полей. На сервере обрезать пробелы заголовка, проверять предел 150 символов, валидировать описание и вложения. Для спецполей проверять обязательность, типы, ограничения и отклонять неизвестные ключи. Привязать заявку к версии схемы, чтобы старые карточки читались после изменения услуги. В одной транзакции атомарно получить следующий номер через обновление счётчика года, записать заявку, выбрать маршрут и записать события создания и маршрутизации. Точный маршрут по подразделению старше общего, затем действует настроенный порядок. Если победителя нет, сохранить «Новая» в очереди разбора с внутренней причиной.
3. **Видимость и чтение.** Ввести единую проверку действия и области доступа. Заявителю доступны его карточки и разрешённые события, исполнителю — назначенные заявки, диспетчеру и руководителю — их рабочие области. Доступ в очередь разбора и право администрировать каталог проверяются отдельно. Для списков применить область видимости до фильтров и пагинации, использовать стабильную сортировку по дате и ID и курсор, привязанный к сортировке. Поддержать фильтры по услуге, статусу, приоритету, периоду и при наличии права по подразделению и исполнителю. Карточку и историю читать по UUID с серверной проверкой.
4. **Рабочий процесс.** Реализовать RPC для допустимых исполнителей, назначения, передачи, изменения срока и приоритета и явных действий по матрице ТЗ. При передаче требовать причину и снимать старое назначение при смене подразделения, если в той же операции не указан допустимый исполнитель. Назначение и переход статуса проверять отдельно. Для уточнения сохранять вопрос и ожидаемую сторону, для подтверждения — результат и подтверждающего. Фиксировать причины отклонения и доработки. Заполнять `completed_at` при выполнении. Проверять ожидаемую версию в транзакции, обновлять запись условно по версии и добавлять события только при успехе. Хранить прежние и новые значения, человека или системного автора и видимость события. Срок и приоритет проверять независимо для каждого изменяемого поля.
5. **Вложения.** Привязывать только временные файлы текущего пользователя и проверять тип, размер и количество. Обеспечить однократное присоединение при параллельных запросах. Если файлы обслуживаются внешней системой, согласовать атомарное резервирование, повторяемое подтверждение и освобождение при откате БД. Для скачивания проверять связь файла с заявкой и видимость. Отдавать клиенту публичные метаданные и разрешённое скачивание без ключей хранилища.
6. **Аналитика и настройки.** Считать агрегаты отдельным запросом поверх ограниченной области видимости. Поддержать группировки из ТЗ по направлению, услуге, статусу, приоритету, подразделению автора на момент подачи, ответственному подразделению, исполнителю и периоду. Считать количество заявок и вложений, длительность по завершённым, текущую нагрузку у действующего исполнителя, активную и завершённую просрочку и заявки без срока. SLA считать только для настроенных услуг по их календарю и правилам пауз. Задокументировать границы периода, знаменатели и формулы. Управление каталогом и маршрутами подключить к административному механизму платформы.
7. **Переключение кабинета и выпуск.** Сгенерировать клиенты и проверить кабинет на актуальном контракте. Подключить настоящую авторизацию, оргструктуру, файлы и администрирование в тестовом окружении платформы. Проверить миграции на чистой базе и на копии текущей схемы с данными. Зафиксировать порядок выкладки, совместимость и порядок отката, команды локального запуска и проверок, подтверждённые интеграции и открытые решения владельца процесса.

## Приёмка

В репозитории не найден набор Go-тестов. В реализацию заложить табличные тесты маршрутизации, прав, валидации и переходов, интеграционные тесты с PostgreSQL для миграций и конкуренции и сквозные проверки через ConnectRPC.

- Уборка с помещением и фотографией проходит от регистрации до подтверждения. Заявитель видит статус и результат.
- Wi-Fi проходит уточнение, ответ, передачу с причиной и выполнение. В истории есть автор и время каждого события, внутренние данные скрыты от заявителя.
- Отсутствующий и неоднозначный маршруты попадают в очередь разбора. Без отдельного права очередь недоступна.
- Запрещены назначение неподходящему сотруднику, недопустимый переход, ответ от другой стороны, прямой доступ к чужой карточке и скачивание чужого файла.
- Параллельная регистрация даёт уникальные номера. Из двух операций по одной версии проходит одна, история соответствует сохранённой версии. При откате события не остаются.
- Аналитика различает заявки в срок, просроченные и без срока. Фильтры не расширяют область доступа.
- После деактивации или изменения схемы услуги старые карточки и отчёты остаются доступными по правам. Новая заявка по деактивированной услуге отклоняется.
