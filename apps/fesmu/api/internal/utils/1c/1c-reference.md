# Справочник по БД 1С (контекст для рефакторинга доступа)

Этот файл — карта того, что и где лежит в SQL-хранилище 1С. Нужен, чтобы
разделить доступ на **общий транспорт** (одно подключение, один читающий
запрос) и **методы по конкретным базам/доменам**.

> Всё, что ниже, получено чтением метаданных и служебных таблиц. Доступ
> только на чтение. Номера таблиц (`_Reference203`, `_AccRg41346` и т.п.)
> **свои в каждой базе** — см. раздел 3, это ключевой момент для архитектуры.

## 1. Топология подключения

```
bibl-03 (RedOS)                     сейчас: WinRM 5985 -> PowerShell на хосте -> TDS 1433
   -> host 192.168.21.6  (C11602B07, DVGMU, Hyper-V)
      -> VM sqlbuhz (192.168.250.2, Windows Server 2012 R2, домен IC)
         -> MS SQL Server 2008 (10.0.6000), instance (local)
```

- SQL-сервер `192.168.250.2:1433` доступен **только с хоста** `192.168.21.6`.
- Временный путь — через WinRM (см. `client.go`).
- Целевой путь после согласования — portproxy `21.6:14330 -> 250.2:1433`,
  тогда бэкенд подключается напрямую через `go-mssqldb`.

## 3. Конфигурации — почему нельзя переносить номера таблиц

Номер в имени таблицы (`_AccRg41346`, `_Reference203`) генерируется 1С при
создании конфигурации. **В разных конфигурациях он разный.** Проверено:

- `bgu2`, `bgu2025` (БГУ ред.2): регистр бухгалтерии = `_AccRg41346`.
- `bgu` (старая ред.): регистр бухгалтерии = `_AccRg770`.

Вывод для архитектуры: **номера таблиц — это параметр конкретной базы**, а не
константа. Либо у каждой базы свой набор констант, либо номера резолвятся из
метаданных на старте (раздел 5). Хардкод чисел, общий на все базы, — ошибка.

Внутри одной конфигурации (все `bgu*` ред.2) номера совпадают, поэтому карту,
снятую с `bgu2025`, можно применять к `bgu2` — но не к `bgu` и не к зарплатным
базам.

## 4. Именование объектов 1С в SQL

| Префикс                | Что это                                   | Примечание                         |
|------------------------|-------------------------------------------|------------------------------------|
| `_ReferenceNNN`        | Справочник (каталог)                      | контрагенты, договоры, номенклатура |
| `_ReferenceNNN_VTMMM`  | Табличная часть справочника               |                                    |
| `_DocumentNNN`         | Документ                                   |                                    |
| `_DocumentNNN_VTMMM`   | Табличная часть документа                 |                                    |
| `_DocumentJournalNNN`  | Журнал документов                         |                                    |
| `_AccRgNNN`            | Регистр бухгалтерии (проводки)            | `_AccRg41346` в БГУ ред.2          |
| `_AccRgATNNN`/`ED`/`CT`| Итоги/субконто регистра бухгалтерии       | остатки и обороты по аналитике     |
| `_AccumRgNNN`          | Регистр накопления (движения)             |                                    |
| `_AccumRgTNNN`         | Итоги регистра накопления                 |                                    |
| `_InfoRgNNN`           | Регистр сведений                          |                                    |
| `_AccNNN`              | План счетов                               | `_Acc54` в БГУ ред.2               |
| `Config`, `DBSchema`   | Служебные: метаданные и схема хранения    | не бизнес-данные                   |
| `_SystemSettings`, `_Users…` | Служебные                          |                                    |

Типовые колонки:
- `_IDRRef` — ключ строки (binary(16)).
- `_Code`, `_Description` — код и наименование (в справочниках, плане счетов).
- `_FldNNN` — реквизит; `_FldNNNRRef` — реквизит-ссылка.
- `_Period` — дата/период (со сдвигом +2000 лет).
- `_Value{1,2,3}_RRRef` — значение субконто (ссылка); `_Value{N}_RTRef` —
  **номер справочника**, на который ссылается субконто (так узнаётся вид
  аналитики: `0xCB`=203, `0x81`=129, `0xE3`=227).

## 5. Как найти нужную таблицу без хардкода

Три способа, от быстрого к правильному:

1. **По плану счетов + `_RTRef`.** Найти счёт в `_AccNN` по `_Code`, взять его
   `_IDRRef`, отфильтровать итоговую таблицу по `_AccountRRef`, а виды субконто
   определить по `_Value{N}_RTRef` (номер = имя справочника `_ReferenceNNN`).
2. **Из метаданных.** Таблицы `Config` / `DBSchema` хранят соответствие
   «объект метаданных → таблица/поле». Разбор сложнее, но даёт полную карту
   для любой базы автоматически.
3. **Через 1С.** Если будет доступ к самой 1С —
   `ПолучитьСтруктуруХраненияБазыДанных()` отдаёт готовую карта «Справочник.X →
   `_ReferenceNNN`, поле → `_FldNNN`». Самый надёжный источник имён.

Для рефакторинга разумно: на старте один раз построить карту (способ 1 или 2)
и закешировать, а не зашивать номера в код.

## 6. Известное сопоставление: задолженность по обучению

Проверено на `bgu2025`/`bgu2` (БГУ ред.2).

- **Счёт**: `205.31` «Расчёты по доходам от оказания платных услуг».
  План счетов — `_Acc54`, счёт ищется по `_Code = '205.31'`.
- **Итоги/остатки**: `_AccRgAT341390`.
  - `_AccountRRef` — счёт.
  - `_Value1_RRRef` → `_Reference203` — **контрагент** (студент/плательщик),
    `_RTRef = 0xCB` (203).
  - `_Value2_RRRef` → `_Reference129` — **договор**, `_RTRef = 0x81` (129).
  - `_Value3_RRRef` → `_Reference227` — **КОСГУ**, `_RTRef = 0xE3` (227).
  - `_Fld41355` — **сумма** (остаток).
  - `_TurnoverDt41370` — оборот по дебету (начислено).
  - `_TurnoverCt41371` — оборот по кредиту (оплачено).
  - `_Period = '5999-11-01'` — служебный период «текущие итоги» (остаток на
    сейчас). Реальные периоды — помесячно (`4026-09-01` и т.п.).
- ФИО/наименование должника — `_Reference203._Description`; текст договора —
  `_Reference129._Description`.

**Важно про смысл.** Остаток по 205.31 — это «сколько осталось заплатить по
договору за весь срок обучения», а не «просрочка». Строки-организации
(например, соглашения с министерством) — не студенты, их надо исключать
(`_Reference129._Description NOT LIKE 'Соглашение%'`). Реальная просрочка
считается только вместе с графиком платежей — источник графика ещё уточняется
у бухгалтерии.

## 6а. Обороты за период (`turnover.go`)

`_AccRgAT341390` хранит обороты **помесячно** (`_Period` = 1-е число месяца,
+2000 лет), точных дат там нет — период всегда расширяется до целых месяцев.
Для месяцев `from…to`:

- **Начислено** = `SUM(_TurnoverDt41370)`, **оплачено** = `SUM(_TurnoverCt41371)`
  по строкам с `_Period` в периоде.
- **Остаток на конец** = текущий остаток (строка `5999-11-01`) минус чистые
  обороты (Дт − Кт) всех месяцев **после** `to`. Текущие итоги 1С включают и
  будущие проводки (в `bgu2` они есть до 31.12.2026), поэтому считать «назад»
  от них корректно.
- **Остаток на начало** = конец − дебет + кредит.
- Группировка по ссылкам (`_Value1_RRRef`, `_Value2_RRRef`), а не по названиям:
  тёзки не склеиваются, КОСГУ (`_Value3`) суммируется.

Данные есть только за период, который лежит в базе (`bgu2`); более ранние годы —
в `bgu20XX` и приходят в `bgu2` вводом остатков.

**Физлицо/организация** (`kind.go`): по ИНН контрагента (10 цифр —
организация, 12 — физлицо/ИП), когда колонка ИНН задана в
`Schema.KontragentINN`. Пока не задана — эвристика по названию: «Соглашение…»,
кавычки, ООО/ГБУЗ/…, слова «министерство», «центр» и т.п. — организация; ФИО —
физлицо.

## 6б. Актуальная задолженность: что проверено (диагностика, 05.10.2026)

Отчёт «Диагностика 1С» на странице задолженности (`diagnose.go`).

- Таблицы итогов: 205.31 и 401.40 — в `_AccRgAT341390` (3 субконто), а также
  без аналитики в `_AccRgAT041369`; 401.10 — в `_AccRgAT241389`.
- Аналитика (RTRef): 205.31 — `0xCB` (контрагенты, 203), `0x81` (договоры,
  129), `0xE3` (КОСГУ, 227). 401.40 — `0xFE` (справочник 254, имя не
  установлено), `0x81` (договоры), `0xE3` (КОСГУ).
- **Остаток 205.31 по договору = вся стоимость договора на весь срок**
  (например, договор от 12.08.2026 — 1 478 400 ≈ 6 лет × ~246 тыс.).
- **Модель «205.31 − 401.40» не подходит:** у проверенных договоров остаток
  401.40 по договору равен 0 (исключение — единичные договоры).
- Помесячно: 12.2025 и 01.2026 — перенос остатков при открытии `bgu2`
  (6,2 и 2,6 млрд по дебету); 09.2026 — 338 млн по ~3 940 договорам, но у
  проверенных договоров сентябрьского начисления нет.

Вывод: актуальную сумму (годовой/семестровый платёж, 170–200 тыс.) можно
получить только из **графика оплаты договора** — его место ищется по карте
метаданных (`metadata.go`: Params.DBNames + Config).

**Найден график (карта метаданных, 05.10.2026):**
`Документ.НачислениеДоходовБудущихПериодовОбразование` = `_Document683`
(проведённых ~99). ТЧ «Начисления» `_Document683_VT10829`:
ИдентификаторСтроки `_Fld10831`, Студент `_Fld10832`, Контрагент `_Fld10833`,
Договор `_Fld10834`, Сумма `_Fld10838`. ТЧ «ПорядокОплаты»
`_Document683_VT10846` (~2 700 строк): ИдентификаторСтроки `_Fld10848`,
ОплатитьДо `_Fld10849`, СуммаПроцент `_Fld10850`, НачалоПериода `_Fld10851`,
КонецПериода `_Fld10852`. Связь строк — по документу и ИдентификаторуСтроки.
Номера — в `SchemaBGU2.Schedule`; точные имена колонок (суффиксы `RRef`,
`_N`, `_T`) определяются по `sys.columns` (`schedule.go`). Открытые вопросы:
охват (у всех ли договоров с долгом есть график) и смысл «СуммаПроцент».

## 7. Предлагаемое разделение архитектуры

Три слоя, каждый со своей зоной ответственности:

**A. Транспорт (общий, DB-agnostic) — `client.go`.**
- `Config`, `New(cfg)`, `(*Client).Query(ctx, sql) ([][]string, error)`.
- Знает про подключение (WinRM сейчас / go-mssqldb потом), read-only guard,
  разбор CSV. Не знает ни про одну базу и ни про один счёт.

**B. Карта базы (per-config) — `schema.go`, `SchemaBGU2`.**
- Структура, которая держит номера таблиц/полей для конкретной конфигурации.
- Заполняется либо константами на базу, либо резолвером из метаданных
  (раздел 5). Именно сюда изолируется различие `bgu2` vs `bgu` vs зарплатных.

**C. Репозитории по доменам (per-DB, бизнес-методы) — `accounting.go`.**
- Используют A (транспорт) + B (карта), отдают доменные структуры.
- Пример метода: `AccountingRepo.ContractBalance(ctx, account string) ([]ContractBalance, error)`
  — счёт передаётся кодом (`"205.31"`), номера таблиц берутся из карты базы.
- Здесь же — доменные типы (`ContractBalance{Kontragent, Dogovor, Ostatok,
  Nachisleno, Oplacheno}`), а не «строки CSV».

Что это даёт:
- Один запрос к 1С (`Query`) — одна точка, где живёт транспорт и безопасность.
- Разные базы (bgu2, зарплатные) подключаются как разные экземпляры карты B и
  наборы репозиториев C, не трогая A.
- Переход с WinRM на прямой SQL меняет только A, сигнатуры B и C неизменны.

**Именование.** Бывший `Debtors205_31` возвращал остаток по
договору — переименован в `Accounting.ContractBalance(ctx, "205.31")` (и
`TuitionBalance` — без соглашений), а слово «должник» оставлено для метода, который
считает просрочку по графику.
